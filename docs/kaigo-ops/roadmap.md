# 介護業務改善 Roadmap

更新日: 2026-09-22
状態: Working roadmap

## Phase 0 — 公開基盤

現在地:

- 介護ルール: 稼働中
- 介護業務改善: 別Vercel Projectとして初期デプロイ済み
- 同一GitHubリポジトリ内の `ops-site/` で管理
- 介護業務改善 → 介護ルールへのリンクあり

次:

- Vercel Project名 / URLを確定
- 介護ルール → 介護業務改善への逆リンクを追加
- Research SiteからProjectとして参照できる状態にする

## Phase 1 — 事前調査基盤

最初にサイト記事を量産せず、調査基盤を作る。

実施:

- 世界の介護DX・AI活用の全体地図
- 国内外の用語辞書
- Evidence register
- 事例schema
- 論文schema
- 更新履歴schema
- 調査終了条件
- 公開前レビュー基準

成果:

- 主要カテゴリ
- Evidenceの厚い領域 / 薄い領域
- 日本に移植しやすい領域
- 初回Issueの優先順位

## Phase 2 — First deep Issue

候補優先順:

1. 必要な情報を探すのに時間がかかる
2. 記録・文書作成に時間がかかる
3. 職員教育・引き継ぎが属人化する
4. 問い合わせ・連携の負担が大きい

初回Issueでは、通常の記事制作より深く調査する。

成果物:

- Source register
- 国内事例
- 海外事例
- 論文
- 公的資料
- 失敗・制約
- 共通パターン
- 日本への適用条件
- Evidence Review
- 利用者向けIssue page

## Phase 3 — 3〜5 Issueで型を検証

目的:

- ページ構造の安定
- 共通schemaの妥当性
- Studio Labでの調査効率
- 更新工数
- 利用者の反応

ここで初めて共通化すべきものを判断する。

先回りして大規模な共通プラットフォームを作らない。

## Phase 4 — 再調査ループ

Issueごとに再調査日を持つ。

```text
publish
  ↓
watch
  ↓
scheduled re-search
  ↓
difference review
  ↓
conclusion changed?
  ├─ NO → 更新履歴のみ
  └─ YES → Evidence / Research Site / Issue page 更新
```

重要なのは「新しい情報が出たか」ではなく「既存の判断が変わるか」。

## Phase 5 — 利用検証

見る指標:

- Issue閲覧
- 原典クリック
- 介護ルール遷移
- 再訪
- ページ滞在
- 実行した改善策
- 判断時間短縮
- 読者からの不足情報
- 検索語

可能なら現場利用者5〜10人程度から定性的なフィードバックを得る。

## Phase 6 — 小規模事業としての検証

無料部分で利用価値が確認できた後に試す。

候補:

- 更新通知
- Issue monitoring
- 実務テンプレート
- チーム用保存・共有
- 比較・診断
- 個別Evidence Brief
- 業界向け定期レポート

価格や機能は先に決めない。

「何に対して支払い意思があるか」を確認してから実装する。

## Phase 7 — 他業界への横展開判断

介護で以下が確認できた場合のみ検討する。

- 3〜5 Issueが継続運用できる
- 更新を半自動化できる
- 実際の利用がある
- 共通化できる調査・表示基盤が見えた

候補業界:

- 建設
- 保育
- 福祉
- 士業
- 製造
- 小売

サイト数を増やすこと自体は目的にしない。

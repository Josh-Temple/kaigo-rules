# Kaigo Ops — フィードバック分類ルール

更新日: 2026-10-07  
対象: Kaigo Ops の公開Issue / action toolから届くGitHub Issues

## 目的

Kaigo Opsのフィードバックは、利用者に長いフォーム入力を求めず、

- 何を試したか
- どこで止まったか
- 何が足りなかったか

の3点を中心に受け取り、次の改善作業へつなげる。

GitHub Issuesを既存の受付先として使い、新しい外部フォーム基盤は追加しない。

## 利用者に求める入力

必須項目を増やさない。Issue routeと、action toolから開始した場合はtool routeをprefillし、利用者は必要な範囲だけ自由記述する。

投稿にはGitHubアカウントでのサインインが必要で、投稿内容はGitHub Issues上で公開・保存される。

氏名、利用者情報、介護記録、事業所の非公開情報は記載しないよう、リンク元とprefillの両方で案内する。

## 内部分類

分類は原則として投稿後に行い、利用者に多数の選択肢を提示しない。

主分類は次の7つとする。

1. 情報不足
2. 手順が分かりにくい
3. toolが使いにくい
4. 制度確認先が分からない
5. 自分の業務に当てはめにくい
6. 既存の方法で足りる
7. その他

必要な場合だけ副分類を1つまで付ける。分類できない場合は「その他」に寄せ、推測で具体化しない。

## 改善判断へのつなぎ方

- 情報不足: Issue本文、根拠、例、前提条件の不足を確認する。
- 手順が分かりにくい: 見出し順、説明、次の操作を確認する。
- toolが使いにくい: 入力前の準備、入力量、結果の読み方、モバイル操作を確認する。
- 制度確認先が分からない: Kaigo Rulesへの具体的な導線と一次資料への戻り方を確認する。
- 自分の業務に当てはめにくい: 対象業務・適用条件・例外条件の説明を確認する。
- 既存の方法で足りる: 新機能追加の根拠にはせず、既存手段を優先できる可能性として扱う。
- その他: 内容を読み、上記のどれにも当てはまらない改善候補だけを個別に扱う。

同じ不足が複数回現れた場合は、再調査またはUI改善の候補とする。ただし、少数の投稿から需要や効果を一般化しない。

## privacy boundary

次の内容は収集対象にしない。

- 氏名
- 利用者情報
- 介護記録本文
- 医療情報
- 非公開の事業所内部情報

これらが誤って投稿された場合、内容を別の台帳や文書へ転載しない。必要なGitHub上の対応だけを行い、改善分析では扱わない。

## 解釈上の注意

- feedback 0件を失敗や需要なしの根拠にしない。
- 1件のfeedbackを全利用者の代表意見として扱わない。
- action tool閲覧だけで、利用完了や改善成功を推定しない。
- 「既存の方法で足りる」は否定的結果ではなく、追加機能を作らない判断材料になり得る。
- pageviewとfeedbackは別の観測値として扱う。

## 変更条件

分類を増やすのは、既存7分類では継続的に扱えないfeedbackが複数確認された場合だけとする。先に分類を細かくして入力負担を増やさない。
